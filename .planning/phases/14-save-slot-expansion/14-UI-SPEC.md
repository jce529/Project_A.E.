# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Platform note:** This is a Unity (C#, uGUI + TextMeshPro) project, not a web/React/Next/Vite
project. The shadcn initialization gate is not applicable — `components.json` was not searched
for and no npm-based component registry exists in this repo. All tokens below are Unity UI
conventions (RectTransform pixel values at the project's existing 1920x1080 Canvas Scaler
reference resolution, `Scale With Screen Size` mode, matched-width). Values were extracted from
the project's existing scenes (`Assets/Scenes/MainMenu.unity`, `Assets/Scenes/Tutorial Map.unity`
— `PauseMenuPanel`/`PanelGame`/`PauseMenuTabController`) rather than invented, to keep the new
Slot Select screen visually consistent with the existing pause/settings UI it is modeled after
(per 14-RESEARCH.md's recommendation to mirror `PauseMenu`'s panel-toggle pattern).

## Design System

| Property | Value |
|----------|-------|
| Tool | none (shadcn not applicable — Unity project) |
| Preset | not applicable |
| Component library | Unity uGUI (`Canvas`/`Image`/`Button`/`Toggle`) + TextMeshPro — existing project convention, no third-party UI kit |
| Icon library | none in use for this phase (slot cards are text-only per CONTEXT.md — visual layout detail deferred, no new icon asset required) |
| Font | NotoSansKR (`Assets/Font/static/NotoSansKR-Regular.ttf` + `NotoSansKR-SemiBold.ttf`) — existing project font family, already used for Korean UI text elsewhere (`GameSettingsPanel` language/toggle labels) |

Canvas Scaler baseline — verified directly against both scene files. `Assets/Scenes/MainMenu.unity`
(line 1210-1215) and `Assets/Scenes/Tutorial Map.unity`'s `PauseMenuPanel` parent canvas (line
4143-4148) share `UI Scale Mode: Scale With Screen Size` and `Reference Resolution: 1920x1080`,
but their `Screen Match Mode` values differ: `MainMenu.unity` uses `m_MatchWidthOrHeight: 0.5`
(line 1215, Width+Height blend) while `Tutorial Map.unity` uses `m_MatchWidthOrHeight: 0` (lines
1342/4148, Width only). An earlier draft of this spec incorrectly claimed both scenes "already
share this setup" — that was false on this one value and is corrected here.

Because the Slot Select screen is entered from the Main Menu
(`MainMenuUI.OnClickStart()`/`OnClickLoad()`) and lives on `MainMenu.unity`'s own Canvas (per the
component library row above), it MUST use `MainMenu.unity`'s existing Match value —
`m_MatchWidthOrHeight: 0.5` — not `Tutorial Map.unity`'s `0`. The overwrite-confirm dialog, as a
child panel of the same Slot Select screen, uses this same `0.5` value for consistency; it never
appears inside `Tutorial Map.unity`.

| Setting | Value |
|---------|-------|
| UI Scale Mode | Scale With Screen Size |
| Reference Resolution | 1920 x 1080 |
| Screen Match Mode | Match Width Or Height = 0.5 (MainMenu.unity's existing value — Slot Select screen inherits this; Tutorial Map.unity's `0` does not apply here) |

The new Slot Select panel and its overwrite-confirm dialog MUST live on this same 1920x1080
reference canvas (`MainMenu.unity`'s existing `Canvas`, or a new sibling Canvas using identical
Canvas Scaler settings) — not the separate 800x600 `Constant Pixel Size` HUD canvas used for
gameplay overlays (`Bottle Panel`, `HP Panel`), which is a different UI layer for a different
purpose.

**Visual focal point:** On the Slot Select screen, the 3 slot cards are the single focal point —
they sit at the visual center of the panel (48px panel-edge padding, 32px inter-card gap, per the
Spacing Scale below), while the panel title ("슬롯 선택") above the row and any back/cancel
affordance below it are secondary, lower-weight elements. Inside the overwrite-confirm dialog, the
destructive confirm button is the deliberate secondary focal point — it draws the eye via the
destructive red color (see Color section) — while the dialog title and body text stay plain white
with no accent, so they don't compete with the confirm button for attention.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps inside a slot card |
| sm | 8px | Gap between slot label and body text within a card |
| md | 16px | Padding inside confirm dialog buttons; gap between dialog title and body |
| lg | 24px | Padding inside each slot card; padding inside confirm dialog panel |
| xl | 32px | Horizontal gap between the 3 slot cards |
| 2xl | 48px | Padding between Slot Select panel edge and the 3-card row |
| 3xl | 64px | Vertical gap between panel title ("슬롯 선택") and the card row |

Exceptions: minimum interactive height for each slot card is 96px (24 x 4) and for confirm/cancel
buttons is 64px (16 x 4) — both remain on-scale multiples of 4, raised above the base scale only
to keep click targets comfortable for a 3-card row layout at 1920x1080. No other exceptions.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | Regular (400) | 1.5 |
| Label | 20px | SemiBold (600) | 1.2 |
| Heading | 32px | SemiBold (600) | 1.2 |
| Display | 72px | SemiBold (600) | 1.2 |

Source/rationale:
- Body 16px matches the font sizes already used inside `PanelGame`/`PanelSound`/`PanelControls`
  in `Assets/Scenes/Tutorial Map.unity` (observed range 14-20px across existing settings rows;
  16px is the mode). Used for: slot card scene name + "격파 보스 N/4" text, confirm dialog body copy.
- Label 20px: slot card header ("슬롯 1" / "슬롯 2" / "슬롯 3"), confirm/cancel button labels.
- Heading 32px: Slot Select panel title ("슬롯 선택"), confirm dialog title ("슬롯 덮어쓰기").
  New size (existing panels don't have a title row this large) — chosen as the next 8pt-scale step
  up from the existing 20px max, kept below the MainMenu's 72px CTA scale since this is a
  secondary/overlay screen, not the main menu itself.
- Display 72px is **not new UI** for this phase — it documents the existing MainMenu button text
  size (`Assets/Scenes/MainMenu.unity`, "Load Game"/"Game Start"/"Option"/"Exit" buttons, all
  `m_fontSize: 72`) which stays visually unchanged; recorded here only so the Slot Select panel
  entry buttons ("이어하기"/"새시작" on the main menu, functionally rewired per D-01/D-02/D-03
  but not restyled) are traceable to a declared size rather than left undocumented.
- Exactly 2 weights declared (Regular 400, SemiBold 600) — both already exist as separate font
  asset files (`NotoSansKR-Regular.ttf`, `NotoSansKR-SemiBold.ttf`), no new font weight needed.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0F141F` @ 96% opacity | Slot Select panel background and overwrite-confirm dialog background — reused verbatim from the existing `PauseMenuPanel` Image color (`Assets/Scenes/Tutorial Map.unity` line 6980: `{r: 0.06, g: 0.08, b: 0.12, a: 0.96}`) |
| Secondary (30%) | `#141A24` @ 90% opacity | Each of the 3 slot card backgrounds (non-selected state) — reused verbatim from `PauseMenuTabController.normalColor` (line 6954) |
| Accent (10%) | `#2673BF` | Reused verbatim from `PauseMenuTabController.selectedColor` (line 6953) |
| Destructive | `#8C2E2E` normal / `#B84747` highlighted / `#611F1F` pressed | Reused from the project's existing destructive-action red family (see justification below) — used only for the overwrite-confirm dialog's confirm button |

Accent (`#2673BF`) reserved for: the currently-highlighted/hovered slot card's border or outline
only, and the "이어하기"/occupied-slot selection state indicator in load-intent mode. Not used for
body text, not used for the empty-slot "새 게임 시작" affordance (that stays in the secondary
card color with white text, matching how normal/unselected `PauseMenu` tabs look today), and not
used for the confirm dialog's "덮어쓰고 시작" button (that button is destructive, see below).

**Destructive color — corrected justification:** An earlier draft of this spec claimed "no
red-family `m_Color` values found in `Tutorial Map.unity`" and introduced a net-new color
(`#D64545`) on that basis. That claim was false: `Assets/Scenes/Tutorial Map.unity` already
contains a red-family destructive button — the `ResetButton` GameObject (fileID `1844472301`,
`Button`/`Image` components at lines 435623-435696) — whose `m_Colors`/`m_Color` blocks (lines
435644-435680) define:

| State | Raw (0-1) | Hex |
|-------|-----------|-----|
| Normal | `{r: 0.55, g: 0.18, b: 0.18}` | `#8C2E2E` |
| Highlighted | `{r: 0.72, g: 0.28, b: 0.28}` | `#B84747` |
| Pressed | `{r: 0.38, g: 0.12, b: 0.12}` | `#611F1F` |

This spec now reuses that existing red family verbatim instead of introducing a new destructive
color, so the new overwrite-confirm button is visually consistent with the game's one other
existing "irreversible action" affordance, per CLAUDE.md's simplicity/no-unrequested-additions
principle (§2) — reusing an established convention rather than inventing a parallel one. The
existing `#8C2E2E` family reads clearly against this dialog's `#0F141F` background (both the
`PauseMenuPanel` background and the `ResetButton` already coexist on the same kind of dark
`Tutorial Map.unity` canvas today, so no new contrast risk is introduced by reusing it here).

Destructive (`#8C2E2E` / `#B84747` / `#611F1F`) reserved for exactly one element: the
"덮어쓰고 시작" button inside the overwrite-confirmation dialog (D-04/D-05) — the button that
actually proceeds with `NewGameInSlot(slot)` and overwrites an occupied slot's save file on the
next disk write. The dialog's "취소" button uses the secondary card color, not destructive red
(cancel is the safe path, not the dangerous one).

Text color on all dark surfaces (panel/card backgrounds above): `#FFFFFF` (white), matching the
existing `PanelGame`/pause-menu text color convention (`Assets/Scenes/Tutorial Map.unity` shows
10 occurrences of `m_fontColor: {r: 1, g: 1, b: 1, a: 1}` inside this same panel hierarchy). Do
not introduce the alternate near-white `#E0F0FF` tint seen elsewhere in the file — that tint is
used by unrelated HUD elements outside this phase's scope, and mixing it in here would add a
second body-text color with no functional reason (CLAUDE.md simplicity principle).

## Copywriting Contract

All new copy is Korean, matching the existing `GameSettingsPanel`/`PauseMenu` convention (Korean
labels: "언어", "화면 흔들림", "튜토리얼 힌트") and the exact Korean wording already locked in
14-CONTEXT.md's D-04. (Note: the *existing* MainMenu button labels — "Game Start", "Load Game",
"Option", "Exit" — are English legacy text; this phase does not touch or retranslate them, since
D-01/D-02/D-03 only change the buttons' *behavior*, not their existing labels/visual style.)

| Element | Copy |
|---------|------|
| Primary CTA (Slot Select panel title) | "슬롯 선택" |
| Slot card label (per card) | "슬롯 1" / "슬롯 2" / "슬롯 3" |
| Slot card body — occupied slot | "{SceneName}" (line 1) + "격파 보스 {BossProgress.Count}/4" (line 2), e.g. "1 stage" / "격파 보스 2/4" |
| Slot card body — empty slot | "빈 슬롯" |
| Slot card CTA — empty slot (new-game intent, D-02/D-03) | "새 게임 시작" |
| Slot card CTA — occupied slot (load intent, D-01) | "이어하기" |
| Empty state heading (all 3 slots empty, load-intent screen only reachable if `loadGameButton` were interactable — see Note below) | "저장된 게임이 없습니다" |
| Empty state body | "새시작 버튼으로 첫 게임을 시작해보세요." |
| Error state (save file exists but fails to parse — `PeekSlotData` catches and returns null while `HasSaveFile` is still true) | Heading: "세이브 데이터를 읽을 수 없습니다" · Body: "파일이 손상되었을 수 있습니다. 이 슬롯에 새 게임을 시작해주세요." (card falls back to the empty-slot "새 게임 시작" CTA — corrupted data is treated as an overwrite-eligible slot, not a dead end) |
| Destructive confirmation — dialog title | "슬롯 덮어쓰기" |
| Destructive confirmation — dialog body (verbatim, locked by 14-CONTEXT.md D-04) | "이 슬롯을 덮어쓰고 새 게임을 시작하시겠습니까?" |
| Destructive confirmation — confirm button | "덮어쓰고 시작" (destructive red `#8C2E2E`/`#B84747`/`#611F1F`, proceeds with `NewGameInSlot(slot)`) |
| Destructive confirmation — cancel button | "취소" (secondary color, closes dialog only, no state change) |

**Button-label rationale (corrects an earlier blocking issue):** the confirm button previously
used the generic label "확인" (OK), which is on the blocklist for destructive dialogs and is not
locked by 14-CONTEXT.md — D-04 only locks the dialog *body* text ("이 슬롯을 덮어쓰고 새 게임을
시작하시겠습니까?"), not the button labels. The confirm button now uses "덮어쓰고 시작"
("Overwrite & Start"), an action-specific label that restates the destructive consequence
(matches the empty-slot CTA wording family, "새 게임 시작", for consistency). "취소" is kept as
the cancel label: it is the safe, non-destructive path, and pairing one specific action-labeled
button ("덮어쓰고 시작") with a plain "취소" is the standard Korean confirm/cancel convention
(e.g. "삭제"/"취소" patterns used throughout Korean software) — the blocklist concern targets a
*pair* of generic labels (확인/취소) where the affirmative action is unclear, not a plain cancel
paired with a specific, named action button.

Note on the "all slots empty" empty state row: per D-01, "이어하기" always opens the Slot Select
screen regardless of save state; per the existing `MainMenuUI.Start()` pattern, `loadGameButton`
is disabled when there is no save at all. Generalizing that existing guard to 3 slots
(`HasSaveFile(0) || HasSaveFile(1) || HasSaveFile(2)`, per 14-RESEARCH.md's Architecture Patterns
section) means the empty-state copy row above is a defensive fallback, not a normally-reachable
screen — documented here so the checker/executor don't have to guess its copy if the button-guard
is ever bypassed (e.g. a future debug/keyboard-shortcut path).
